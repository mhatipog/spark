# Prospective N32 preregistration — before first SQL run

We deliberately designed N *after* observing M, but every N row and query is new. The dev v2 grammar, all original JVM guards and this N32 scorer have exact Git blob pins in PROTOCOL.json. The first N experiment is not a random draw from production use; it measures a targeted generalization hypothesis after four development replays.

- 32 cases, 8 SQL families × 4 independent table instances.
- 8 direct integer extrema groupings (`MAX`, `MIN`), 8 nested `COUNT`/`MAX`, deliberately enriched for new dev proof fragments.
- 16 honest outside-fragment controls: inner join, left join, DISTINCT, HAVING; zero proofs for these is an acceptable outcome.
- 2 integer tables per case, duplicated rows, NULL fields, zero and negative values, new deterministic seed 2026102014. Spark and SQLite must agree as **unordered bags** before any proof coverage is interpreted.
- All 32 cases must execute, trace with no cap/errors, resolve exactly one post-Finish Analysis optimizer suffix each and pass the independent observer-integrity checks.
- Primary metric is complete changed optimizer-suffix conditional proof chains **and** all independent frame/RDD-input/all-rule/tag gates; report each separately. Preserve UNKNOWN for unsupported rules.
- Report target-vs-generalization challenge coverage, per-family counts, all observer failures and provenance even if N yields zero successes.
- Under no circumstance reinterpret M’s 20/48 prospective first-run result after seeing N.

No attempt at ordered-result proofs, error preservation, whole-engine correctness, or superiority over existing kernel-checked SQL provers.

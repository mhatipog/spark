# QueryProof — automatic global ordering obligation extraction (2026-10-17)

## Main result: implemented and independently executed

**Two official released Spark versions passed the frozen experiment:** [Actions 39062616527](https://github.com/mhatipog/spark/actions/runs/39062616527), jobs for 4.0.1 and 4.2.0 successful. This branch is research-only and does not modify Apache Spark upstream PR #59445.

We extended our earlier *manually keyed* observable ORDER BY checker with `plan_extractor.py`. It reads Spark's `QueryExecution.analyzed` logical plan through Catalyst JVM objects, unwraps an explicitly enumerated set of order-preserving root operators, verifies that the remaining operator is a **global** `Sort`, and resolves each `SortOrder.child` by `exprId` against the analyzed plan's exposed output attributes. It obtains ASC/DESC and NULLS FIRST/LAST from Spark's own `SortOrder`; only integral scalar keys are accepted.

The formerly manually supplied order keys in the existing **frozen** manifest were used *only as scoring labels*, not for extraction. The extracted obligations were then checked against the same actual returned rows using the established independent Python adjacent-pair comparator.

| Experiment | Spark 4.0.1 | Spark 4.2.0 |
| --- | ---: | ---: |
| Supported holdout runs (15 SQL families × AQE on/off) | 30/30 exactly matched independently labelled key specs | 30/30 |
| Unsupported controls (derived/hidden sort expression and partition-local SORT BY, × AQE on/off) | 4/4 UNKNOWN | 4/4 UNKNOWN |

| Extraction, execution or unit-test failures | 0 | 0 |

**This is 60 supported holdout executions, not 60 unrelated correctness issues.** All 15 holdout families were expected to be correct in these configurations. The known bug was not newly discovered. Coverage is limited to final output sort obligations with exposed integer keys and a small set of root wrappers; other cases must explicitly return UNKNOWN. Successful observable order checks still do not validate correct row bags, selected top-k members, aggregates, subquery values, or the Spark planner's overall soundness.

## Why this matters

The prior stage required a human to read SQL and manually specify the sorting keys. Now the system obtains these from Spark's *resolved* analyzed plan with expression identities instead of textual guesses. This reduces manual setup and provides a concrete basis for studying preservation of semantic obligations across runtime query-plan rewrites.

This is **not a novel theory** and does not establish autonomous general SQL verification. Work on SQLancer's NoREC/TLP/DQP/CODDTest and the recent DistSQL comparator must be treated as relevant baselines before a research publication. No external comparator was executed in this experiment.

## Next falsifiable step

Automatically isolate a **safe** nested `ORDER BY + LIMIT/OFFSET` selection stage from Catalyst CTE and subquery plans, derive the ordering keys and independent source relation, and produce a bounded top-k membership witness **only if** the source relation, identity mapping, deterministic selection order and boundary values are fully established. Else return UNKNOWN. Exercise the known PR #59445 family and negative controls, including filters, joins, hidden keys, tied order values and multiple candidate boundaries. Compare with the earlier manually configured stage-based checker. Do not claim an oracle where a source relation is guessed.

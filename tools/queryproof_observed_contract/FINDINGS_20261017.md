## What has actually been shown?

An explicit witnessed decrease of exposed integer ORDER BY keys in adjacent output rows is a **genuine local ordering-contract failure**, requiring neither a second SQL reference run nor trust in Spark's physical-plan ordering metadata. The 17-case frozen manifest and mutation tests establish that the implementation exercises null policies, reverse order, ties and diverse *correct* query shapes.

For a totally preordered key tuple, transitivity gives the elementary equivalence:

    (for every adjacent i: K(row_i) <= K(row_(i+1)))
     iff
    (for every i < j: K(row_i) <= K(row_j)).

This checks observable monotonicity *only*. It says nothing about whether the right rows were returned, whether a LIMIT chose the true top-k, aggregate values, SQL equivalence, optimizer soundness, or whether hidden order keys were respected.

The external comparator is not SQLancer, SQLSolver, DistSQL or SQL query-equivalence testing. We did **not** execute any of those baselines. These are deliberately small, hand-selected SQL families—not a random sample of real workloads, independently identified defects, or a discovery-rate benchmark.

## Strongest scientific interpretation

- The earlier pure structural ranking scored **0/3** on independently reproduced held-out bugs; these new results do not rehabilitate it.
- Physical metadata's declaration \`GLOBAL_ORDER_NOT_ESTABLISHED\` must not be interpreted as incorrect execution; the observable comparator separately witnesses actual wrong order when ordering keys are exposed.
- A simple contract checker reliably catches this known AQE issue while making no false accusations on these held-out controls.
- This is **engineering validation**, not enough novelty for a database-systems research publication by itself. Sorting output keys and checking neighbors is elementary.
- The important remaining research challenge is automatically extracting trusted semantic obligations from arbitrary optimized plans, including hidden ordering keys and LIMIT/OFFSET membership, while keeping false accusations and runtime overhead rigorously bounded.

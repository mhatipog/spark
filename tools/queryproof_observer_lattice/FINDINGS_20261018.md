# QueryProof — automatic SQL 3VL witness and exact observer partitions
### Research results verified on 18 October 2026

**State: implementation milestone achieved, general scientific novelty unproven.**

Parent lineages:

## Achievement A — independently witness wrong SQL row bags

Branch: [Catalyst 3VL witnesses](https://github.com/mhatipog/spark/tree/research/queryproof-catalyst-3vl-witness-20261018/tools/queryproof_catalyst_3vl)

Validated in BOTH official unmodified Spark 4.0.1 and 4.2.0, with AQE enabled and disabled:
[Actions 39104441431](https://github.com/mhatipog/spark/actions/runs/39104441431) — both jobs succeeded.

The supported engine-independent oracles work from the **analyzed Catalyst plan**, resolving raw input views and expression identities. The data reader retrieves small source inputs and the Python interpreter computes results **without asking Spark to evaluate the target join or IN predicate**.

**Inner join:** A conservative subset of analyzed plans with a direct Project over a direct INNER JOIN of two small in-memory registered Parquet views. Supported deterministic operators: AttributeReference, Literal, EqualTo, EqualNullSafe, Not, And, Or, IsNull, IsNotNull. Cartesian source pairs and SQL strong-Kleene three-valued logic give an independently computed **multiset** of projected outputs. The interpreter records a concrete missing/extra row witness.

- Known B01 / SPARK-58384: caught in **4/4** (2 versions × AQE on/off) executions; old detector missed it. Three-valued truth table for B01 has one matching TRUE pair of six input pairs, two FALSE, and three NULL.
- Additional `NOT` and `IS NULL` variants in same failure family were also witnessed on both releases; these are NOT new bug families.
- Safe positive-equality, null-safe equality, and plain NOT-controls returned no false violation verdicts in the tested scope.
- LEFT OUTER JOIN, derived project, unsupported < predicate, and no-join controls returned UNKNOWN (never given a fabricated result).

**Nullable IN:** Another conservative interpreter handles a direct Filter with one uncorrelated scalar InSubquery and direct source views. SQL IN is independently computed, including NULL semantics and empty inner-set behavior.

- Known B02 / SPARK-58442: caught in **4/4** executions across both releases and AQE modes.
- A separate `IS NOT NULL` variant of the same family also returned a wrong-result witness.
- Direct IN, NOT IN, and OR controls were accepted; computed output, filtered subquery, absent subquery and projected value contexts returned UNKNOWN.

Together the interpreters cover **two distinct already known historical wrong-result families, B01 and B02**, with the SQL outputs independently reconstructed rather than passed in from a hand-written oracle. B03 (uncorrelated IN over global aggregate's empty source) is **still unsupported**; its scalar/global-aggregate semantics require a separate preservation obligation.

This work assumes independent replayable small source views, exact integer/null semantics, and no row-source mutation. It does NOT generalize to arbitrary Spark SQL, user-defined functions, joins with multiplicity not represented by the narrow interpreter, nonintegral comparisons, or complex correlated subqueries. Runtime costs include an additional scan and Cartesian pair enumeration; production overhead is unmeasured.

## Achievement B — complete observation-partition lattice

Branch: [five-element observer lattice](https://github.com/mhatipog/spark/tree/research/queryproof-observer-lattice-20261018/tools/queryproof_observer_lattice)

Exhaustive standard-library-only mathematical tests:
[Actions 39104838751](https://github.com/mhatipog/spark/actions/runs/39104838751) — five tests passed, including all unary/binary operator truth tables, all five partitions, and nested three-level paths with every independent sibling valuation.

For D = {T, F, U}, there are exactly Bell(3)=5 partitions into observational equivalence classes:
1. {T,F,U}: no observation of the value (ANY)
2. {T},{F,U}: TRUE_ONLY
3. {F},{T,U}: FALSE_ONLY
4. {U},{T,F}: NULL_ONLY
5. {T},{F},{U}: FULL_3VL

For operator f, a required output partition P, and a selected input i, define child equivalence

    x ~_(f,P,i) y  iff  for all sibling input assignments s,
       [f(s with child_i=x)]_P = [f(s with child_i=y)]_P.

This is the **coarsest sound** local partition under independent sibling valuations. Proof: pairs with identical signatures are indistinguishable for every sibling valuation; each distinguished pair has a concrete sibling assignment witnessing the P-observable difference. This is standard finite-state partition refinement / abstract interpretation, not original mathematics.

Examples derived *without manual equivalence labels*:
- NOT with a TRUE_ONLY observing parent requires FALSE_ONLY on its child.
- IS NULL with TRUE_ONLY observer requires NULL_ONLY on its child.
- Positive AND/OR under TRUE_ONLY observer require TRUE_ONLY on each Boolean child.
- Some NULL_ONLY observations through AND/OR force FULL_3VL.

In a fully enumerated synthetic universe of 3^3 = 27 unary maps D→D and 27×27 = **729 ordered replacement pairs**, exact FULL_3VL permits 27 pairs; TRUE_ONLY, FALSE_ONLY, and NULL_ONLY each permit 125 pairs. This is **98 additional mathematically safe replacements** for those abstract observation contexts. These are synthetic abstract functions, **not actual Spark optimizer rewrites or measured performance gains**. The lattice could reduce unnecessary verifier abstention when integrated correctly.

## Achievement C — automatic observation-demand extraction from Catalyst

The tool [catalyst_observer.py](catalyst_observer.py) reads `QueryExecution.analyzed` and recursively walks the actual Spark logical expression AST, beginning with Filter/Join root-TRUE obligations or Project/Aggregate output FULL_3VL obligations. It propagates observation partitions through recognized SQL Boolean operators and safely defaults to FULL_3VL for unknown expression contexts. It never reads expected answer labels, SQL substrings or optimized-plan result rows.

An evaluation set of five known case/target labels was frozen **before** implementing the new extractor: [FROZEN_CATALYST_OBSERVER.json](FROZEN_CATALYST_OBSERVER.json).

Both official Spark versions independently passed:
[Actions 39105077386](https://github.com/mhatipog/spark/actions/runs/39105077386).

| Historical case | Catalyst target | Demand automatically derived | Predeclared label |
|---|---|---|---|
| B01 SPARK-58384 | OR under JOIN NOT | FALSE_ONLY | FALSE_ONLY |
| N01 safe nullable JOIN | direct OR under JOIN | TRUE_ONLY | TRUE_ONLY |
| B02 SPARK-58442 | IN under filter IS NULL | NULL_ONLY | NULL_ONLY |
| N02 safe IN filter | direct IN under Filter | TRUE_ONLY | TRUE_ONLY |
| B03 SPARK-58429 | IN in global Aggregate output | FULL_3VL | FULL_3VL |

**5/5 target obligations in each Spark version; no plan-extraction errors.** No actual optimizer rewrite witness was claimed from this obligation-extraction experiment alone.

## Scientific novelty and strict next milestone

**Engineering validation: strong for the stated narrow scopes.**
**Independent generalized detection: not yet demonstrated.**
**Publishability as a novel database-systems method: not yet justified.**

Key remaining problem is **rewrite-level provenance**. Given an *analyzed* demanded observation partition, automatically identify the relevant optimized transformation, map pre/post subexpressions with valid identity and binding provenance, and construct a finite witness when the rewrite violates that demanded partition. Need account for optimizer changes to the plan *shape*, not only changed expression text. A simple comparison of analyzed-plan strings and optimized-plan strings is NOT a proof.

Design a new evaluation using genuinely unseen bug families/versions, with frozen exclusion of the development bugs, and compare to an actually executed SQLancer DQP/NoREC/TLP/CODDTest baseline (or precisely labeled independent reimplementation). Report the numerator of confirmed new issue-family detections, false accusations, UNKNOWN fraction, and overhead.

The SPARK-58442 and SPARK-58429 upstream PRs are already open; do not submit duplicate fixes. Our separate Spark PR #59445 remains open and untouched.

All code/data here synthetic and tested in lightweight branch-specific Actions, not the huge upstream Spark build.

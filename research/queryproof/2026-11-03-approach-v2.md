# Interface hunt, phase two: a better approach (2026-11-03)

This document is written before any phase-two run. Phase one (pairs one to four,
`2026-11-01-interface-results.md`) stays frozen.

## Why change

Phase one in numbers:
- **Yield:** the spec method found 5 new bugs in 22.7 engine core-hours, the matched random
  baseline 3 in 22.0. The whole lead comes from pair one, and later pairs found 0–1 new bugs
  each.
- **Rediscoveries:** we found more already-reported bugs (N4, N5, SPARK-60797, SPARK-59605,
  trinodb#27274/#30544/#31908, datafusion#18083, ORC-2226) than new ones.
- **Noise:** pair four's 33,000 findings were triaged by hand into 2 new bugs.

Three observations drive the redesign:

1. **The single-engine on/off oracle is being taken over by the projects themselves.**
   DataFusion is adding a differential fuzz test that runs each case with
   `pushdown_filters` on and off ([apache/datafusion#25453](https://github.com/apache/datafusion/pull/25453)),
   and arrow-rs is extending its reader fuzzing to predicate pushdown
   ([apache/arrow-rs#10823](https://github.com/apache/arrow-rs/pull/10823)). Bugs that one
   engine can find on its own will increasingly be found in that engine's CI.
2. **The ground is crowded, and the bug study says where the bugs are.** From 10 trackers
   (DuckDB, Polars, ClickHouse, Arrow C++, arrow-rs, DataFusion, Trino, delta-rs, Iceberg,
   iceberg-rust), we took the issues created from 2026-08-01 that mention Parquet, ORC or
   partitions. 153 of them report a wrong, dropped or silently corrupted result. By title,
   they split as follows (first match wins; `mine/` in the scratchpad):

   | Class | Issues | Covered in phase one? |
   | --- | --- | --- |
   | Partition directories and partition values | 32 | Only from pair four |
   | **Writers that write unsound metadata** (statistics, null_pages, page index, histograms, empty pages) | 24 | **No:** only pyarrow and parquet-mr wrote files, and nothing checked what they wrote |
   | Table-format metadata (Delta, Iceberg, Hudi, Paimon) | 17 | No |
   | Optimizer (TopN, window, join) | 14 | Out of scope |
   | **Cast and mixed-type predicates unwrapped for pruning** | 11 | **No:** every template compares a column with a literal of its own type |
   | NaN and signed zero | 6 | Yes (O3, D3) |
   | Other | 49 | |
3. **The literature has better oracles than ours for the same idea.**
   - **Radar** (VLDB 2024, "Detecting Metadata-Related Logic Bugs in Database Systems via
     Raw Database Construction", [PDF](https://www.vldb.org/pvldb/vol17/p1884-song.pdf)):
     the same data under different metadata must give the same answer. Our writer axis is
     this idea applied to files, but we used only two writers.
   - **SQLancer++** ("Scaling Automated Database System Testing",
     [arXiv:2503.21424](https://arxiv.org/pdf/2503.21424)): breadth over 18 DBMSs found 196
     new bugs. Breadth over engines pays more than depth in one.
   - **Test reuse across systems:** "Understanding and Reusing Test Suites Across Database
     Systems" ([arXiv:2410.21731](https://arxiv.org/html/2410.21731v1)); BugForge,
     [arXiv:2604.03024](https://pith.science/paper/2604.03024), reports 62% transfer
     success across DBMSs. SQL dialects limit how far tests transfer, but **a file is a
     lingua franca:** a bug-triggering file transfers to every engine without translation.
   - **DQP, TQS, MOZI, MPE** (several plans or configurations for one query): our
     skipping on/off switches are a configuration oracle of this kind, and we keep them.

## The new approach: "every writer × every reader, and check the writer too"

### O1. Metadata soundness oracle (new; the subject is the writer)

For every file any writer produces, an independent auditor decodes the footer itself
(Thrift compact protocol, `parquet.thrift` from parquet-format master). It checks every
claim the file makes against the values that are actually in it:

- **Statistics:**
  - Row-group statistics must be sound bounds under the column's sort order (signed,
    unsigned, byte-wise unsigned for strings and binary, value order for decimals, no
    order for INT96).
  - `null_count` must be exact when present.
  - `is_min_value_exact` and `is_max_value_exact` must be honest.
  - The deprecated `min`/`max` fields must not be the only bounds on a byte-array column
    with signed order.
  - NaN must not be min or max.
  - `nan_count`, when present, must be exact.
- **Page index:**
  - `ColumnIndex.null_pages` must be true exactly for pages with no non-null value.
  - `min_values`, `max_values` and `null_counts` must be sound per page.
  - `boundary_order` must hold.
  - `OffsetIndex.first_row_index` must be increasing and consistent with the row-group
    row count.
- **Bloom filters:** each must contain every non-null value. We probe with our own
  split-block filter and xxHash64 over the plain encoding of the physical type.
- **Dictionary:** a chunk whose `encoding_stats` say "all data pages dictionary-encoded"
  must have every value in its dictionary.
- **Size statistics and level histograms:** when present, they must match the data (the
  Arrow C++ bug [apache/arrow#50778](https://github.com/apache/arrow/issues/50778)).
- **Structure:** `num_rows` must add up; no data page may have zero values in a
  non-empty chunk (the pattern of [#54533](https://github.com/apache/arrow/issues/54533)
  and [#55342](https://github.com/apache/arrow/issues/55342)).

A violation is a writer bug whether or not any reader trips over it. No query is needed,
there are no engine semantics to triage, and the signal is precise: one claim, one
column, one row group or page.

### O2. Full writer × reader matrix (extends phase one)

- **Writers** (each with the settings that push skipping structures onto a few rows):
  - pyarrow and Spark (parquet-mr, orc-java), as in phase one;
  - **Polars**, **DuckDB `COPY`**, **DataFusion `write_parquet`** (arrow-rs) and
    **fastparquet**;
  - **chDB** (ClickHouse's writer, CI only).
- **Readers:** Spark, Trino, DuckDB and DataFusion as before, plus **Polars**
  (`scan_parquet` with statistics on and off), **pyarrow.dataset** (row-group statistics
  filtering) and **chDB** (native and Arrow readers, filter and bloom pushdown on and off).
- **Oracle:** unchanged (skipping on vs off per reader, and skipping off vs the Python
  answer). Because the logical rows are the same for every writer, a reader that answers
  differently for two writers' files of the same rows is a Radar-style finding, even
  without the Python answer.

### O3. Cast and mixed-type templates (new; from the bug study)

Templates that make an engine unwrap or move a cast to prune:
- `CAST(ts AS DATE) = d` and `CAST(ts AS DATE) < d`;
- `date_col = TIMESTAMP '…'`;
- `int_col = 1.5`, `int_col < 2.5` and `int_col IN (1.0, 2.5)`;
- `CAST(int_col AS BOOLEAN)`;
- `CAST(str_col AS INT) = v` and `CAST(str_col AS DATE) < d`;
- `decimal_col = v` with v at a larger scale;
- `CAST(bigint_col AS INT)` and its narrowing overflow;
- `try_cast` and `TRY_CAST`, where the engine has them.

The Python answer is computed with each engine's documented cast semantics where those
are standard. Engine-specific semantics (for example, what a string-to-int cast does with
`' 1'`) are compared only skipping on vs off.

### O4. Bug transplantation (new)

Each wrong-result bug from the catalogue in `mine/` whose trigger is a file plus a
predicate becomes a shape, written by every writer and read by every reader. A bug fixed
in one engine is a test for the others. Phase-one examples:
- SPARK-60797 (decimal partition scale);
- datafusion#26491 (signed zero in bloom filters);
- duckdb#27863 (INT96 statistics from parquet-mr 1.8.1);
- polars#30043 (unsigned statistics merged with signed order);
- iceberg-rust#3264 (page-index pruning on INT32-encoded decimals).

### Automatic triage

- `known_issues.json` holds signatures: engine, kind, a regex over the error or the
  qid/shape, and the issue link. It is applied before any human sees a finding.
- Findings are clustered by (engine, kind, normalised error or result shape, writer), and
  a person looks at one representative per cluster.
- O1 findings are clustered by (writer, claim, physical type).

## Baseline and accounting

- The matched random baseline stays. It gets the new writers, readers and the auditor,
  because those are harness capabilities. It also gets a generic cast atom
  (`CAST(col AS random type)` compared with a random literal), because a cast template is a
  query feature, not a contract-derived value.
- Phase-two results are reported separately from phase one, per method and per oracle.
- **Cost** is engine core-hours, plus the auditor's core-hours under its own heading.

## Rounds

1. **Round A:** O1 and O2 (new writers and readers) over all existing shape sets (spec1–4
   and random seeds 1–5). This is pure breadth: the shapes are already written, so a new
   finding is attributable to the new axis.
2. **Round B:** O3 (cast templates), spec and random alike.
3. **Round C:** O4 (transplanted shapes).
4. **Round D (if time allows):** table formats (Delta via delta-rs/Spark/Trino/DuckDB/Polars,
   Iceberg via pyiceberg/Spark/Trino/DuckDB): deletion vectors, column mapping, schema
   evolution and manifest statistics. This is where 17 of the 153 recent bugs sit.

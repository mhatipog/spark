# QueryProof bug hunt — Spark 4.2.0 (23 October 2026)

## Question

Can the QueryProof tooling find real optimizer bugs in the current Spark release
(pyspark 4.2.0), and are any of them new?

## Method

- **Generator.** `gen_hunt.py` emits queries from 17 SQL families with a history
  of bugs: EXISTS and IN subqueries (correlated and NOT), the COUNT bug, nested
  EXISTS, semi-join under OR, scalar subqueries, outer-join chains with IS NULL
  filters, aggregates with joins, DISTINCT aggregates, FILTER clauses, set
  operations, ORDER BY…LIMIT/OFFSET, CASE/NULLIF, windows with RANK filters
  (InferWindowGroupLimit), derived tables, and Spark-only constructs (ROLLUP,
  INTERSECT/EXCEPT ALL, LATERAL, LEFT ANTI, multi-column IN). Tables are small,
  integer-only, about 30% NULL, and contain duplicate rows.
- **Oracles** (`run_hunt.py`):
  - FULL: the default optimizer.
  - MINIMAL: every excludable rule excluded.
  - NOCODEGEN: whole-stage codegen off, interpreted expressions.
  - SQLITE: an independent engine.
  - Results are compared as bags. A crash under a supported configuration counts
    as a finding.
- **Single-rule ablation** (`run_ablation.py`): each of the 94 excludable rules is
  excluded on its own. `spark.sql.optimizer.excludedRules` is a public
  configuration, so Spark must still plan the query and return the FULL bag.
- **Second engine** (`hunt_duckdb.py`): the same cases on DuckDB 2.0.0, compared
  with SQLite and with DuckDB itself under `PRAGMA disable_optimizer`.
- **Runs.** All runs use the public fork, on GitHub-hosted runners only.

## Results

| Run | Scale | Wrong-answer mismatches | Crash disagreements |
| --- | --- | --- | --- |
| Pilot (local; MINIMAL still excluded RewriteWithExpression) | 40 queries × 2 datasets | 0 | 8, all finding 1 |
| CI run 40021220952 (seed 20261027), 4 oracles | 1,200 × 2 = 2,400 runs | 0 (vs MINIMAL, NOCODEGEN, SQLite) | 14, all finding 2 (MINIMAL; OFFSET 0) |
| CI run 40023050226 (seed 20261029), single-rule ablation | 95 rules × 600 queries = 55,195 runs | 0 | 52: 17 finding 3 (all with OFFSET), 35 finding 1 (all with NULLIF) |
| DuckDB 2.0.0 vs SQLite 3.50.4 and DuckDB without its optimizer (seed 20261028) | 30,000 × 3 = 90,000 runs | 0 | 0 (1,017 parse errors: DuckDB has no `LEFT ANTI JOIN` syntax) |

## Findings

| # | Configuration | Symptom | Status upstream |
| --- | --- | --- | --- |
| 1 | `RewriteWithExpression` excluded | `NULLIF` → `[INTERNAL_ERROR] Cannot generate code for expression: with(...)` | **Known, fixed on master:** SPARK-59019 (2026-08-31; rule made non-excludable). Still present in 4.2.0. |
| 2 | `EliminateOffsets` excluded | any top-level `OFFSET 0` → bare `java.lang.AssertionError` in `CollectLimitExec.<init>` (from `SpecialLimits`) | **Known, fixed on master:** SPARK-59044 (2026-10-05; the planner handles `Offset(0)`). Still present in 4.2.0. |
| 3 | `ConstantFolding` excluded | any `LIMIT k OFFSET m` → `AssertionError: No plan for LocalLimit (k + m)`, because `LimitPushDown` emits `LocalLimit(Add(le, oe))` and the planner matches only `IntegerLiteral` | **Known, open:** SPARK-57125 (2026-05-28). Unchanged on master (`Optimizer.scala` still emits `Add(le, oe)`; `SparkStrategies` still matches `LocalLimit(IntegerLiteral)`). |

All three are the same class of bug: an excludable rule that the planner depends
on. Upstream has been fixing this class one rule at a time (SPARK-59019,
SPARK-59044, SPARK-59682 for `RemoveRedundantAliases`). The QueryProof hunt
rediscovered three of them independently from random queries, which validates
the method. None of the three is a new finding.

## What it does not show

- No wrong-answer (as opposed to crash) bug was found in any oracle. This is
  bounded evidence over small integer databases and these 17 families. It is not
  evidence that the optimizer is correct.
- The QueryProof kernel certifies only the rule/grammar subset in V22. Hunt
  queries with subqueries, windows or aggregates fall outside it, so the
  per-event REWRITE triage in `triage_hunt.py` was not the source of these
  findings.
